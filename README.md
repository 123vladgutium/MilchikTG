# MilchikTG 2.0 — запуск без сервера приложения

Проект использует HTML, CSS и обычный JavaScript. Supabase подключается через официальный JS SDK с CDN. Серверный код в этом проекте не нужен.

## Что уже реализовано
- Настоящая регистрация и вход по email/паролю через Supabase Auth.
- Профиль с отображаемым именем и кратким описанием.
- Поиск пользователей по отображаемому имени.
- Создание личных чатов через защищённую SQL-функцию.
- Хранение сообщений в PostgreSQL.
- Обновление новых сообщений через Supabase Realtime.
- Поиск по существующим чатам.
- Адаптивный интерфейс для телефона и компьютера.
- Восстановление пароля по email.
- Убраны демо-аккаунты и локальная фальшивая база.

## Часть 1. Создать Supabase-проект
1. Открой https://supabase.com/ и зарегистрируйся.
2. Создай новый project. Сохрани пароль базы данных в безопасном месте.
3. Открой SQL Editor → New query.
4. Открой файл `supabase-schema.sql` из архива, скопируй весь текст, вставь в редактор и нажми Run.
5. В Dashboard открой Project Settings → API (в некоторых интерфейсах — Connect).
6. Скопируй Project URL и **publishable key** (или legacy `anon` key). Не копируй `service_role` или secret key.

## Часть 2. Подключить ключи
1. Открой `script.js`.
2. В самом начале замени:
   - `PASTE_YOUR_SUPABASE_PROJECT_URL_HERE` на Project URL;
   - `PASTE_YOUR_SUPABASE_PUBLISHABLE_KEY_HERE` на publishable/anon key.
3. Сохрани файл.

Публичный publishable/anon key допустимо использовать в браузере только вместе с правильно настроенной RLS. Никогда не вставляй service_role/secret key в `script.js` или публичный GitHub-репозиторий.

## Часть 3. Настроить Auth
1. В Supabase открой Authentication → URL Configuration.
2. Добавь адрес сайта GitHub Pages в Site URL и Redirect URLs.
   Пример: `https://ВАШ-USERNAME.github.io/ВАШ-РЕПОЗИТОРИЙ/`
3. Для тестирования можно оставить подтверждение email включённым. После регистрации нужно перейти по ссылке в письме.
4. Для восстановления пароля проверь настройки email и Redirect URLs.

## Часть 4. Опубликовать на GitHub Pages
1. Открой https://github.com/ и создай новый репозиторий, например `milchiktg`.
2. Загрузи в корень репозитория эти файлы:
   - `index.html`
   - `style.css`
   - `script.js`
   - `supabase-schema.sql` (это файл схемы; он не исполняется на GitHub Pages)
3. Открой репозиторий → Settings → Pages.
4. В разделе Build and deployment выбери `Deploy from a branch`.
5. Выбери ветку `main` и папку `/ (root)`, нажми Save.
6. Подожди завершения публикации и открой адрес, который покажет GitHub Pages.
7. Добавь этот адрес в Supabase → Authentication → URL Configuration.

## Часть 5. Проверить
1. Открой сайт в обычном окне браузера.
2. Создай аккаунт с email, к которому есть доступ.
3. Подтверди email, если Supabase попросит.
4. Открой сайт в другом браузере/приватном окне и зарегистрируй второй аккаунт.
5. Из первого аккаунта найди второго по отображаемому имени и открой чат.
6. Отправь сообщение, затем ответь из второго аккаунта. Новые сообщения должны появляться без ручной перезагрузки.

## Если не работает
- `Invalid API key` / ошибка соединения: проверь Project URL и publishable/anon key в `script.js`.
- После регистрации нет входа: проверь email и подтверждение аккаунта в Authentication → Users.
- `relation does not exist`: SQL из `supabase-schema.sql` не запускался полностью.
- `permission denied` / `row-level security`: проверь, что SQL выполнился без ошибок и policies созданы.
- Не приходит realtime: Supabase Dashboard → Database → Replication/Realtime и убедись, что таблицы `messages` и `conversation_members` добавлены в `supabase_realtime`.
- Поиск находит людей только по имени — это текущая реализация; поиск по email намеренно не открыт, чтобы не раскрывать адреса пользователей всем участникам.
- Если ты меняешь проект на публичный, протестируй все правила доступа двумя разными аккаунтами.

## Важно
Это базовая рабочая основа личного мессенджера, не полная копия Telegram. В этой версии нет групп, звонков, push-уведомлений, вложений, блокировок и сквозного шифрования. Не используй её для хранения чувствительных данных. Перед реальным публичным запуском стоит добавить ограничение частоты сообщений, жалобы/блокировки, правила хранения и удаления данных, а также провести аудит безопасности.
